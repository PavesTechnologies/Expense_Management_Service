02

Split Validation & Management

Business outcomeAn employee can split one expense line item across 2 or more Cost Centers, by percentage or by fixed amount — with the system guaranteeing the split always adds up exactly to the line item total, and never silently merging or guessing at ambiguous input.

Locked rules

Rule 1 — a split set is 0 rows (normal expense) or 2+; exactly 1 is always rejected.
Rule 2 — the same Cost Center twice on one line item is rejected outright, never auto-merged.
Rule 3 — FIXED_AMOUNT splits must sum to the line item total within ±0.01, no rounding absorption.
Rule 4 — PERCENTAGE splits must sum to 100% within ±0.01%.
Rule 5 — for PERCENTAGE mode, the rounding remainder is absorbed entirely into the last split in entry order, so the stored sum reconciles exactly.
All splits on one line item share one mode — PERCENTAGE and FIXED_AMOUNT can never mix within the same line item.

New DTOs

ExpenseSplitRequest
costCenterId, splitType, percentage, allocatedAmount
ExpenseSplitReplaceRequest
List<ExpenseSplitRequest> — whole-set replace, not per-row CRUD
ExpenseSplitResponse
splitId, lineItemId, costCenterId/Name, splitType, percentage, allocatedAmount, splitOrder, createdAt

Endpoints

  • GET
    /xms/employee/expense-line-items/{lineItemId}/splitslist the current splits
  • PUT
    /xms/employee/expense-line-items/{lineItemId}/splitsreplace the whole set; roles ADMIN/GENERAL/FINANCE/MANAGER, ownership enforced in the service

Authorization is deliberately stricter than the legacy CostAllocationService it sits alongside: every call requires the acting employee to own the report, and the report must be in an editable status.

03

Budget Encumbrance Engine

Business outcomeBudget is now reserved the moment a report is submitted, not when it's finally paid — so two people can no longer both spend the same last dollar of a Cost Center's budget while their reports are mid-approval. Admins also get three new budget controls: carrying forward unused budget from a prior year (capped), a low-budget warning, and an explicit "allow spending with no budget configured" override.

Effective Available Budget

availableBudget − SUM(amount) across every ACTIVE BudgetEncumbrance against that budget row

Never stored — computed at read time, every time. CostCenterBudget.availableBudget itself is never touched by encumbrance logic; only the existing, unmodified consumeBudget() ever changes it, and only at AP payment (Phase 6).

BudgetEncumbranceService (new)

validateAndEncumber(report, cycle)
atomic all-or-nothing; locks every distinct Cost Center's budget row in sorted UUID order (deadlock-safe); same Cost Center across several splits is checked once, combined
releaseActiveForCycle(reportId, cycle)
ACTIVE → RELEASED; no-op if none active
consumeActiveForReport(reportId, cycle)
ACTIVE → CONSUMED via the existing consumeBudget; returns whether anything was found
effectiveAvailable(budget)
the read-time formula above

New budget-policy fields

CostCenterBudget.rolloverFromPrevious
validated ≤ MIN(source's true unencumbered remainder, rolloverCap)
allowRollover, rolloverCap, warningThreshold
admin-set per budget row
CostCenterBudgetRequest.rolloverSourceBudgetId
request-only, never persisted — fiscalYear is free text, so "last year's row" can't be auto-derived safely
CostCenter.allowUnbudgeted
lets a Cost Center accept encumbrances with zero budget configured
First pessimistic lock (PESSIMISTIC_WRITE) ever introduced in this codebase — used only by validateAndEncumber, never by consumeBudget.

Built and fully tested standalone in this phase — deliberately not yet called from submission or AP completion, so the capability could be verified in isolation first (wired in Phases 5 & 6).

04

Approval Routing for Splits

Business outcomeWhen an expense is split across Cost Centers, each Cost Center's own owner now approves their own portion — not one person rubber-stamping the whole report. If the same person owns two of the split Cost Centers, they get one combined task, not two. A report that's part split, part normal still needs both the split owners and the original approver to sign off.

Locked design decisions

Split-owner assignments always activate immediately, in parallel — the level's SEQUENTIAL/ANY_OF/ALL_OF quorum only governs its normal (non-split) entries, since each owner approves a disjoint slice with nothing to sequence.
Scoped to APPROVAL-type levels only; Finance Verification is untouched this phase.
A split-owner assignment auto-skipped by the existing duplicate-approver pass has its splits waived from level completion — the same reasoning as why that skip exists at all.

Core mechanics

createSplitOwnerAssignments
resolves one owner per distinct split Cost Center; same-owner splits combine into one ApprovalAssignment
isEntireInstanceDone
= normal line-item track done AND every non-skipped split-owner's own splits approved
reviewSplit(reportId, splitId, actor, decision)
the split-aware sibling of reviewLineItem — one owner's rejection never blocks a different owner

Endpoint

  • POST
    /xms/approvals/{reportId}/splits/{splitId}/reviewapprove or flag one split's Cost Center Owner responsibility
Zero changes needed to ChainCorrectnessServiceImpl or DefaultApproverSourceResolverImpl — both already operate generically on ApprovalAssignment rows, so self-approval redirect and duplicate-skip work on split-owner assignments for free (proven for real in Phase 8).

05

Correction & Encumbrance Lifecycle

Business outcomeReserved budget doesn't sit "phantom-locked" forever — the moment a report is cancelled, recalled, rejected, or fully restarted after correction, its budget reservation is released, and a fresh one is made only if the report is actually resubmitted.

Where encumbrances get created

submit()
validateAndEncumber runs before the approval chain is even materialized — insufficient budget aborts with nothing created
fullRestart()
releases the old cycle first, then encumbers the new one — so the same money is never double-counted against itself

Where encumbrances get released

cancelAllOpenInstances()
the single existing choke point already used by recall, cancel, rejectReport, and full-restart's old-cycle teardown — one change covers all four
resumeInPlace()
deliberately untouched — a same-cycle Manager correction never re-validates the encumbrance amount (documented, accepted gap)
+7 tests encumber-on-submit · insufficient-budget-abort · release-on-recall/cancel/reject · resume-in-place untouched · restart ordering (release-then-encumber, verified in sequence)
06

AP Payment Completion

Business outcomeWhen Accounts Payable marks a report paid, the org's real budget is decremented correctly per Cost Center a split touched — not as one lump sum against the report's header Cost Center — and, for a foreign-currency expense, in the correctly converted amount.
Bug found & fixed — currency basis ExpenseSplitServiceImpl (Phase 2) was splitting lineItem.amount — the line item's own display currency — instead of lineItem.baseAmount, the Org Base Currency figure that CostCenterBudget is actually denominated in. BudgetEncumbranceServiceImpl's unsplit-remainder sum had the same issue. Invisible for a base-currency line item (the two are equal there); real for any foreign-currency one. Fixed in both classes, with your explicit sign-off to reopen two already-confirmed phases; 2 new tests prove it with a foreign-currency fixture (amount = 10000, baseAmount = 8500).
BudgetEncumbranceService.consumeActiveForReport
now returns boolean — found-and-consumed vs. nothing-to-consume
ApprovalWorkflowService.getCurrentSubmissionCycle(reportId)
new — lets AP ask "which cycle" without depending on the approval engine's own repository
ApPaymentServiceImpl.markPaymentCompleted
tries encumbrance-based consumption first; falls back to the original direct consumeBudget(costCenter, fiscalYear, report.totalAmount()) call only when a report has zero encumbrances at all — covering reports already in flight before this wiring existed, with no double-consumption possible

07

Queue, History & Bulk Approve

Business outcomeA Cost Center Owner now sees their own pending splits in "My Approvals," can see the full review history of every split on a report, and can bulk-approve everything they personally have pending in one action — without ever touching a different owner's work.
Bug found & fixed — wrong assignment marked complete reviewLineItem's authorization lookup didn't exclude split-owner assignments. A split-owner who also happened to be resolvable for the shared line-item review would have their own split-owner assignment wrongly marked COMPLETED — even though their actual splits were still untouched. Fixed by excluding assignments with any split reviews from that lookup; surfaced by the very bulk-approve scenario this phase added.

Cross-Cutting Integration Testing

Business outcomeProof the whole system works together, end to end — not just each piece in isolation. This is exactly the class of testing that caught the two bugs found in Phases 6 and 7.

New test class SplitApprovalBudgetIntegrationTest wires the real ApprovalWorkflowServiceImpl + ChainCorrectnessServiceImpl + BudgetEncumbranceServiceImpl together (repositories mocked, no database) — a new pattern for this codebase, where every other test mocks out the other collaborators.
